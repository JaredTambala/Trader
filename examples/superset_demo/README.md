# Local Apache Superset evaluation

This is a separate, local-only read-only exploration stack for the Superset evaluation initiative. It does not run the
Trader Console frontend or API, and it never uses ambient `PG_*` settings. The stack has two PostgreSQL databases:

- `trader`: synthetic Trader data and the producer-owned `console_read` contract;
- `metadata`: writable Superset metadata (datasets, charts and dashboards).

The database is the boundary. Trader produces domain evidence and producer-owned typed views; Superset reads those
PostgreSQL surfaces directly. Nothing in Trader core, the backtest runtime, research services, or the Console API calls
Superset or publishes dashboard state. This example owns only isolated demo setup and Superset metadata. Its fixture
generator is not a general backtest publication API.

The external Superset connection uses a dedicated `superset_demo_reader` role for its synthetic fixture. When the
repository `.env` contains the explicit local Trader PostgreSQL settings, the helper also registers **Trader local
data** through `host.docker.internal` and exposes the producer-owned `console_read.stock_bars` view for real
Alpaca-loaded bars. This is a local developer connection; Superset UI write restrictions are not the database security
boundary.

## Start the trial

Requirements: Docker Desktop with WSL integration, Python 3.12 with `uv`, and loopback ports available on `25433`,
`5008` and `8088`. Run from the repository root. The helper creates `examples/superset_demo/.local/credentials.json` with mode
`600`; do not copy, print or commit that file.

<!-- verified: integration:superset tests/cross_package/workflows/test_superset_demo.py -->
```bash
uv run python -m examples.superset_demo up
```

Open `http://127.0.0.1:8088` and use the `admin` account. Read the password from the private credentials file locally.
The registered datasets are **Trader synthetic demo → `console_read.stock_bars`** (three `DEMO` / `1Min` setup rows)
and, when `.env` is configured, **Trader local data → `console_read.stock_bars`** (the real Trader event-store view).
The latter currently contains the TRD-215 Alpaca backfill: 18,786 1-minute rows across 69 symbols, covering
2026-08-13 through 2026-09-11 UTC. The dashboards **Trader demo · MCP · bars** and **Trader real · MCP · bars** are
generated by Superset's built-in MCP server (port `5008`), with close-price, volume and raw OHLCV table views. The MCP
client is idempotent for those title prefixes; it does not edit or delete unrelated Superset assets.

The MCP-created exploration dashboards are:

- **Trader explore · Data coverage** — stored-row and symbol counts, observed bars by UTC day, symbol coverage ranking,
  and a complete per-symbol inventory.
- **Trader explore · Price and volume** — zoomable observed-minute close/volume views with close as a line and volume
  on a secondary bar axis, plus a raw OHLCV table with up to 20,000 rows. The shared Symbol filter selects the series;
  the chart's horizontal time navigation handles dense minute ranges.
- **Trader explore · Activity and data checks** — observed volume, UTC-hour activity, stored-value checks, and the
  longest observed timestamp intervals. Intervals include overnight/weekend closures and are not labelled missing bars.

These dashboards query the real local database directly through Superset MCP. They do not poll automatically; use
Refresh to re-query. Each dashboard now has shared **Symbol** and **Bar time (UTC)** native filters. The filters target
the underlying stock-bar charts and compatible exploration datasets; chart-level Explore remains available for deeper
inspection.

The registered `console_read` contract is producer-owned. Release 3 adds lifecycle identity projections and backtest
evidence coverage for review dashboards; the Superset demo does not fabricate those identities or infer missing causal
links. Comparative cohorts consume the producer-owned scope and variant fingerprints; Superset does not invent
compatibility keys.

## Generate backtest review fixtures

The backtest review data is generated by a demo-owned fixture adapter that invokes Trader's production `BacktestRunner`
and event-store persistence path. The
deterministic bars are replay inputs only; run lifecycle, orders, fills, positions, metrics snapshots and experiment
metadata come from the hot path. The command is restricted to the dedicated Superset demo database and clears only its
own `superset-backtest-fixture` namespace before rerunning:

<!-- verified: integration:superset tests/cross_package/workflows/test_superset_demo.py -->
```bash
uv run python -m examples.superset_demo fixtures
```

It creates completed/drawdown, zero-trade, multi-symbol, partial, missing-mark and failed-run cases. Repeating the
command produces the same six experiment rows and run counts without touching the existing Trader database. The
backtest review views are then available under `console_read.backtest_*` for Superset dataset registration.

The **Trader backtest · MCP · single-run review** dashboard is seeded from the nine summary projections, four
producer-owned lifecycle/evidence projections, and the typed comparison-scope projection. It has run overview and performance tables, strategy-versus-benchmark
equity, exposure and positions, executed trades, assumptions, warnings, provenance, signal lifecycle, order lifecycle,
fill lifecycle, evidence coverage and comparison scope. Use the shared **Backtest run** filter to keep every panel on one `run_id`, and
**Observation time** to constrain time-aware panels. The lifecycle tables keep `signal_event_id`, `order_event_id`,
`fill_event_id` and `client_order_id` visible; null links are shown as unlinked evidence rather than inferred from
timestamps. The equity panel remains a normal Superset time-series chart, so its zoom controls are available for dense
runs. Strategy and benchmark are separate series; the dashboard does not imply that a benchmark is a strategy result.

The separate **Trader backtest · MCP · comparison · review** dashboard is explicitly cohort-scoped. Select one
`scope_fingerprint` before viewing normalized strategy/benchmark equity, drawdown, or the cohort run table. Variant
strategy identities remain visible, and legacy runs without scope metadata remain unavailable for comparison.

## Inspect the generic Candlestick prototype

Superset 6.1's server registry and MCP chart discriminators contain no candlestick entry. Official Superset guidance
requires a frontend visualisation plugin registered in the frontend preset. This initial experiment therefore keeps the
database boundary intact and exports a bounded, generic Apache ECharts prototype from the same
`console_read.stock_bars` contract. It includes OHLC candles, linked volume, crosshair, inside/slider zoom and empty
event-marker hooks; it contains no Trader-specific chart type or API.

Generate it with `uv run python -m examples.superset_demo candlestick --symbol DEMO --limit 2000`.

Open `examples/superset_demo/.local/candlestick.html` in a browser. The exported rows are read through the dedicated
Superset demo reader. This is a visual contract probe, not a replacement for the eventual Superset visualisation
plugin; the next implementation task must build and register that plugin in a demo-owned Superset image. Generic event
annotations can be populated from producer-owned lifecycle data in a later slice.
This export is not integrated into Superset and has not been visually qualified. It currently uses the synthetic demo
database, not the real Alpaca dataset, and loads ECharts 6.0.0 from jsDelivr. The categorical time axis compresses every
unobserved interval, including gaps: it does not distinguish market closures from missing observations. A single
symbol is mandatory and duplicate timestamps are rejected. Session-aware navigation, time-range selection, actual
event overlays, real-data integration and browser verification remain outstanding in TRD-232.

The dashboard seed uses Superset's MCP server for datasets, charts and dashboard creation. Superset 6.1 does not
expose native-filter metadata in the MCP dashboard schema, so the idempotent seed completes the two shared filters
through Superset's supported dashboard REST endpoint. It owns only the `Trader backtest · MCP` titles and the two
`NATIVE_FILTER-TRADER-*` metadata entries.

<!-- verified: integration:superset tests/cross_package/workflows/test_superset_demo.py -->
```bash
uv run python -m examples.superset_demo check
```

`check` queries the real Superset API and proves the three-row preview, then reconciles the `run_id` rows in all sixteen
backtest, lifecycle, scope and comparison datasets against direct queries through the dedicated PostgreSQL reader. It
also checks both review dashboards, lifecycle/comparison charts and their shared filters. The permission workflow disables the reader's default
transaction read-only setting and proves
that writes, DDL, unapproved source reads and unapproved view reads fail; the disposable probe is removed afterwards.

## Stop and repeat

<!-- verified: integration:superset tests/cross_package/workflows/test_superset_demo.py -->
```bash
uv run python -m examples.superset_demo down
uv run python -m examples.superset_demo up
```

The metadata and Trader volumes are retained, so the registered dataset and Superset objects survive a restart. There
is intentionally no manual reset command: the named test workflow owns disposable volumes, while the manual demo must
not be accidentally truncated.

To run the isolated workflow, which creates a unique project and volume and removes only those resources:

<!-- verified: integration:superset tests/cross_package/workflows/test_superset_demo.py -->
```bash
SUPERSET_DEMO_TESTS=1 uv run pytest tests/cross_package/workflows/test_superset_demo.py -q
```

The workflow is not part of the ordinary offline suite. It repeats the fixture safely, reconciles the database-backed
datasets, exercises database stop/restart recovery, and confirms retained Superset metadata. Record the Superset image,
driver, repository revision, fixture counts, commands and results in TRD-224. This task does not qualify
complete-dataset search, production deployment, authentication integration or the future Trader API.

## Port overrides

Use explicit local ports when the defaults are occupied:

<!-- verified: integration:superset tests/cross_package/workflows/test_superset_demo.py -->
```bash
uv run python -m examples.superset_demo up --database-port 25434 --ui-port 8089 --mcp-port 5009
uv run python -m examples.superset_demo check --database-port 25434 --ui-port 8089 --mcp-port 5009
```

The helper still fixes the database name, roles and Compose project. It does not accept a DSN or a general database
selector.
